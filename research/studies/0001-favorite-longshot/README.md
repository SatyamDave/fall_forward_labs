# Study 0001: favorite-longshot bias on settled Kalshi binary markets

First bounded research cycle (research-loop spec §5 A-I). The frozen plan is `REGISTRATION.md` and `config.json`, committed before any settled outcome was fetched. Results are in `RESULTS.md` and `results.json`, generated by code; the verdict and the evidence are summarized in the PR.

## Authorization assumption

Consequential assumption, made by the agent on 2026-09-27 and stated here so a founder can reverse it: read-only, unauthenticated `GET` requests to Kalshi's public market-data endpoints are allowed. No API keys, account endpoints, orders, demo trading or paid services were used. The hard budget was 3000 HTTP requests including retries and documentation fetches, paced at 2 requests per second, a tenth of the Basic read budget (200 tokens/s at 10 tokens per request, [rate limits](https://docs.kalshi.com/getting_started/rate_limits.md), accessed 2026-09-27). That page says every authenticated request costs tokens; how unauthenticated requests are limited is not documented (UNKNOWN).

## Files

- `kalshi_client.py`: budgeted GET client; every request, retry and failure goes to `data/raw/study-0001/requests.jsonl`, which is also the budget counter.
- `fetch.py`: listing, sampling and trade fetch into `data/raw/study-0001/` (gitignored by the existing `data/raw/` rule), then writes `data/catalog/study-0001.json` (sha256 of every raw file, request counts, cutoffs, fetch times).
- `study.py`: selection, features, chronological split, leakage guard, metrics, decision. Offline.
- `tests/test_leakage.py`: the leakage guard passes clean rows and trips on a price after its decision time, a label field in a feature row, and a train label settling after the first test decision.
- `tests/test_recompute.py`: recomputes the primary metric straight from the raw JSON with separate code and asserts equality. Skips when the snapshot is absent (CI has no raw data).
- `record_trial.py`: appends the one registered trial to `research/registry/trials.jsonl` via `registry.record`; refuses a second append for the same config hash.

## Commands

- `just study-0001`: rerun the analysis from the saved snapshot and the study's tests. Needs the snapshot in `data/raw/study-0001/`; to rebuild it, run `python3 fetch.py` from this directory, which spends up to the request budget.
- `cd research && uv run python studies/0001-favorite-longshot/record_trial.py`: one-time registry append (already done for this config).

## Run report (2026-09-27): blocked by the registered listing rule

Verdict: INSUFFICIENT EVIDENCE. No outcome was analysed; the hypothesis is neither supported nor refuted (UNKNOWN).

- Registration commit `a299ba1` at 2026-09-27T23:11:07Z, pushed 23:11:15Z. First settled-outcome request 23:13:18Z (`data/catalog/study-0001.json`, `first_settled_outcome_fetch_at`). VERIFIED.
- Public endpoints worked without credentials: 495 of 497 API requests returned 200; the other 2 were local DNS failures, retried successfully. No 429. VERIFIED (`requests.jsonl`, ledger sha256 in the catalog).
- Every settlement day from 2026-08-01 to 2026-09-09 filled all 12 pages of 1000 with a cursor still pending, so each has more than 12,000 settled non-combo markets. The registered rule drops such a day whole, so all 40 were dropped and the eligible population is empty. VERIFIED (ledger; the fetch loop only stops early on an empty cursor). The agent stopped the fetch at request 497 once this was clear, rather than spend the rest of the budget on days the rule would also drop; days 2026-09-10 to 2026-09-19 were not listed.
- Design faults this exposed, both mine: the per-day cap was set without measuring listing volume, which is not an outcome and could have been measured before registration; and the fetcher deleted the pages of dropped days, so 487 successful requests left no reusable data. Seven partial pages of 2026-09-10 remain on disk, hashed in the catalog and unused.
- The analysis code, leakage guard and independent recomputation were exercised only on a SYNTHETIC calibrated fixture inside `tests/test_recompute.py` (plumbing only, not evidence of anything about Kalshi).
- `just study-0001` reproduces `results.json` exactly (sha256 `115aca07...8cc92e0a8` on two runs).
